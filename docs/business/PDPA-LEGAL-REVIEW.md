# PDPA Legal Review — ระบบ "Smart Cam Sale"

**จัดทำโดย:** ที่ปรึกษากฎหมายคุ้มครองข้อมูลส่วนบุคคล
**วันที่:** 28 สิงหาคม 2569
**อ้างอิงกฎหมาย:** พระราชบัญญัติคุ้มครองข้อมูลส่วนบุคคล พ.ศ. 2562 ("PDPA")
**ขอบเขต:** ตรวจสอบจากโค้ดจริงใน `apps/api/prisma/schema.prisma` และ `apps/api/src/` ประกอบกับสถาปัตยกรรมที่แจ้ง (Azure SEA, Neon Singapore, Anthropic API US)

> **สรุปผู้บริหาร:** ระบบออกแบบมาโดยคำนึงถึง privacy ระดับหนึ่ง (ไม่เก็บภาพ, guest log ไม่มี identity, มี endpoint ลบ embedding) แต่**ยังขายเชิงพาณิชย์ไม่ได้ในสภาพปัจจุบัน** — จุดตายคือ (1) API ไม่มี authentication เลย ทำให้ข้อมูลสมาชิกและภาพกล้องเปิดสาธารณะ ขัดมาตรา 37(1) โดยตรง (2) ระบบสแกนใบหน้า*ทุกคน*ที่เดินผ่านกล้องเพื่อ match กับฐานสมาชิก = ประมวลผลข้อมูลชีวภาพของผู้ไม่ให้ความยินยอม (3) consent เป็นแค่ boolean ใน DB ไม่มีหลักฐานพิสูจน์ได้ (4) ยังไม่มี DPA และเอกสารประกอบสำหรับลูกค้า B2B

## 1. การจำแนกประเภทข้อมูล

| ข้อมูล | ที่อยู่ในระบบ | ประเภทตาม PDPA |
|---|---|---|
| Face embedding 512 มิติ | `FaceEmbedding.embedding` (schema.prisma) | **ข้อมูลชีวภาพ = ข้อมูลอ่อนไหว (มาตรา 26)** |
| ชื่อ, เบอร์โทร, อีเมล, เพศ, ปีเกิด | `Member` | ข้อมูลส่วนบุคคลทั่วไป |
| ประวัติซื้อ, tier, แต้ม | `Purchase`, `PurchaseItem` | ข้อมูลส่วนบุคคลทั่วไป (ผูกกับ memberId) |
| VisitLog ของสมาชิก | `VisitLog` ที่มี `memberId` | ข้อมูลส่วนบุคคลทั่วไป (พฤติกรรม identity-linked) |
| VisitLog ของ guest | `VisitLog` ที่ `memberId = null` | ข้อมูลนิรนาม (อายุประมาณ/เพศ/เวลา ไม่ระบุตัวได้) — **ผลลัพธ์**ไม่เป็นข้อมูลส่วนบุคคล |

**ประเด็นสำคัญ 3 ข้อ:**

**(ก) Face embedding เป็นข้อมูลอ่อนไหวแม้ไม่เก็บภาพ** — มาตรา 26 วรรคท้ายนิยาม "ข้อมูลชีวภาพ" ว่าเป็นข้อมูลที่เกิดจากการใช้เทคนิคเฉพาะที่ทำให้สามารถยืนยันตัวบุคคลได้ เช่น ข้อมูลจำลองใบหน้า — embedding 512 มิติที่ใช้ match ตัวบุคคลคือกรณีนี้ตรงตัว การ "ไม่เก็บภาพ" ช่วยลดความเสี่ยง (data minimization ที่ดี) แต่**ไม่เปลี่ยนประเภทข้อมูล**

**(ข) การประเมินอายุ/เพศของ guest "นับเป็นการประมวลผลข้อมูลส่วนบุคคล"** — แม้ผลลัพธ์สุดท้าย (VisitLog นิรนาม) จะไม่เป็นข้อมูลส่วนบุคคล แต่*ระหว่างทาง* ภาพใบหน้าถูกส่งขึ้น cloud, ผ่าน InsightFace, และถูกสร้าง embedding — ภาพใบหน้าเป็นข้อมูลส่วนบุคคลตั้งแต่วินาทีที่กล้องจับได้ การประมวลผลชั่วคราวใน memory ก็คือ "เก็บรวบรวมและใช้" ตามกฎหมาย จุดยืน "เราไม่บันทึกจึงไม่เข้า PDPA" **ใช้ไม่ได้** — ที่ถูกคือ "เราประมวลผลแบบชั่วคราวโดยมีฐานกฎหมายรองรับและลบทันที"

**(ค) โค้ดจริงประมวลผลชีวภาพของ guest มากกว่าที่ claim** — จาก `src/recognition/recognition.service.ts`:
- `processFace()` เรียก `findClosestMember(face.embedding)` กับ**ทุกใบหน้า** — แปลว่า guest ทุกคนถูกสร้าง embedding และนำไปเทียบกับฐานข้อมูลชีวภาพ นี่คือ facial recognition ต่อบุคคลที่ไม่เคยให้ความยินยอม ไม่ใช่แค่ "ประเมินอายุ/เพศ"
- `rememberEmbedding()` / `rememberChannelEmbedding()` cache embedding ล่าสุดของ*ทุกคน* (รวม guest) ไว้ใน memory ของ server โดย map แบบ per-channel **ไม่มีการล้างเมื่อ disconnect** — embedding ของ guest ค้างอยู่ในระบบจนกว่าจะถูกทับ

## 2. ฐานทางกฎหมายรายกรณี

| กิจกรรม | ฐานที่เหมาะสม | ความเห็น/ความเสี่ยง |
|---|---|---|
| เก็บ embedding สมาชิก | **ความยินยอมโดยชัดแจ้ง (explicit consent) ตามมาตรา 26** เท่านั้น | ข้อยกเว้นอื่นของ ม.26 ใช้ไม่ได้กับ marketing/CRM — ปัจจุบันระบบมีแค่ `faceOptIn` boolean ที่โค้ด set เป็น `true` เองอัตโนมัติใน `members.service.ts` (`enroll()` และ `registerFace()`) **ไม่มีบันทึกเวลา ข้อความ consent ที่ใช้ หรือหลักฐานการให้** — พิสูจน์ต่อ สคส. ไม่ได้ = เสี่ยงสูง |
| ชื่อ/เบอร์/ประวัติซื้อ/แต้มสมาชิก | สัญญาสมาชิก (มาตรา 24(3)) | ปลอดภัย — แต่ถ้าใช้ส่ง marketing เพิ่มเติมต้องมี consent แยก |
| ประเมินอายุ/เพศ guest แบบไม่เก็บ | ประโยชน์โดยชอบด้วยกฎหมาย (มาตรา 24(5)) | พออ้างได้ *ถ้า* แจ้งด้วยป้ายชัดเจน + ลบทันที + ทำ balancing test เป็นเอกสาร แต่ต้องระวังไม่ให้ขั้นตอนใดแตะระดับ "ระบุตัวบุคคล" |
| **สแกน+match ใบหน้า guest กับฐานสมาชิก** | **ไม่มีฐานที่มั่นคง** | จุดเสี่ยงที่สุดของระบบ — การเทียบ embedding ของผู้ไม่เป็นสมาชิกกับฐานชีวภาพเป็นการ "ใช้" ข้อมูลชีวภาพโดยไม่มี consent อ้าง ม.24(5) กับข้อมูลอ่อนไหวไม่ได้ (ม.26 ไม่เปิดช่อง legitimate interest) ทางรอดเชิงเทคนิค-กฎหมายคือทำให้การ match เป็น ephemeral โดยสมบูรณ์ (ประมวลผลแล้วทิ้งทันที ไม่ cache) และเปิดเผยในป้าย/notice ว่ามี face recognition สำหรับสมาชิก พร้อมช่องทาง opt-out ระดับร้าน — แต่ต้องยอมรับว่านี่เป็น grey zone ที่ สคส. อาจตีความเข้มได้ |
| ส่งข้อมูลไป Claude (Anthropic US) | ฐานเดียวกับ CRM + จัดการข้ามพรมแดน (ดูข้อ 5) | โค้ด (`claude-script.service.ts`) ส่ง displayName, tier, แต้ม, visitCount, totalSpend, ชื่อสินค้าที่ซื้อบ่อย — เป็นข้อมูลส่วนบุคคล (ระบุตัวได้เมื่อประกอบกัน) ควร minimize |

## 3. บทบาท: บริษัท = ผู้ประมวลผล, ร้านค้า = ผู้ควบคุม

โมเดล B2B SaaS นี้ ร้านค้าเป็น**ผู้ควบคุมข้อมูล** (กำหนดวัตถุประสงค์: CRM ของร้านตัวเอง) และบริษัทเราเป็น**ผู้ประมวลผลข้อมูล**ตามมาตรา 40 ผลที่ตามมา:

1. **ต้องมีข้อตกลงการประมวลผล (DPA) เป็นลายลักษณ์อักษรกับทุกร้าน** — มาตรา 40 วรรคสามบังคับให้มีข้อตกลงควบคุมการประมวลผลระหว่าง controller กับ processor **ปัจจุบันยังไม่มี template นี้ = ขายไม่ได้ตามกฎหมาย**
2. บริษัทประมวลผลได้เฉพาะตามคำสั่งร้านค้า (ม.40(1)), ต้องจัดมาตรการความปลอดภัยและแจ้งเหตุละเมิดให้ร้านทราบ (ม.40(2)), ต้องทำบันทึกรายการกิจกรรมประมวลผลฝั่ง processor (ม.40(3))
3. **กับดักสำคัญ:** ถ้าบริษัทใช้ข้อมูลจากร้านเพื่อวัตถุประสงค์ตัวเอง (เช่น train/ปรับ model, ทำ analytics ข้ามร้าน) บริษัทจะกลายเป็น controller ในส่วนนั้นทันที (ม.40 วรรคสอง) — รับหน้าที่และโทษเต็มรูป ต้องเขียนขอบเขตใน DPA ให้ชัด
4. Sub-processor ทั้งหมด (Azure, Neon, Anthropic) ต้องระบุใน DPA และร้านต้องรับทราบ

| มาตรการความปลอดภัย | ม.37(1) | **ล้มเหลวในปัจจุบัน — ช่องโหว่จริงจากโค้ด:** (1) API ทั้งหมดไม่มี authentication — `GET /members` เปิดชื่อ/เบอร์/แต้ม, `GET /members/:id` เปิดประวัติซื้อเต็ม, `DELETE /members/:id/face` ใครก็เรียกได้ (2) WebSocket `cors: { origin: '*' }` (recognition.gateway.ts) + `broadcastFrame` ส่งภาพกล้องดิบให้ใครก็ตามที่ join channel (3) รหัสผ่านกล้องเก็บ plaintext (schema.prisma บรรทัด `password String // NOTE: stored plaintext for MVP`) (4) `$queryRawUnsafe`/`$executeRawUnsafe` กับ embedding — ควร review injection surface |
| แจ้งเหตุละเมิด 72 ชม. | ม.37(4) | **ยังไม่มีกระบวนการ** — controller (ร้าน) ต้องแจ้ง สคส. ภายใน 72 ชม. เมื่อมีความเสี่ยง; ฐานะ processor เราต้องแจ้งร้าน "โดยไม่ชักช้า" (ม.40(2)) → ต้องมี incident response plan + ช่องทางแจ้งร้านอัตโนมัติ |

## 5. การส่งข้อมูลข้ามพรมแดน (มาตรา 28–29)

ข้อมูลเก็บและประมวลผล**นอกประเทศไทยทั้งหมด**:

| ปลายทาง | ข้อมูลที่ข้ามแดน | การจัดการ |
|---|---|---|
| Azure Southeast Asia (สิงคโปร์) — compute/InsightFace | ภาพใบหน้า (ชั่วคราว), embedding | สิงคโปร์ยังไม่อยู่ในรายชื่อประเทศที่ สคส. ประกาศว่ามีมาตรฐานเพียงพอ → ต้องอาศัยมาตรการที่เหมาะสมตาม ม.28(5)–(6)/ม.29 เช่นข้อสัญญามาตรฐาน — Microsoft DPA + SCC ของ Azure ใช้อ้างได้ ต้องเก็บเอกสารไว้และระบุใน Privacy Notice |
| Neon (สิงคโปร์) — Postgres | embedding, ข้อมูลสมาชิก, ประวัติซื้อ, VisitLog | เช่นเดียวกัน — ตรวจ DPA ของ Neon ว่ามี transfer clause; **ย้ำ: ข้อมูลอ่อนไหว (embedding) ข้ามแดน หากไม่มีมาตรการรองรับ โทษปกครองขยับไปเพดาน ม.84** |
| Anthropic API (สหรัฐฯ) | displayName, tier, แต้ม, visitCount, totalSpend, สินค้าที่ซื้อบ่อย; guest: อายุ/เพศโดยประมาณ | จุดที่หลวมที่สุด: (1) ควร**minimize** — ส่งเฉพาะ tier + หมวดสินค้า ตัด displayName/แต้ม ออกได้โดยคุณภาพสคริปต์แทบไม่เสีย (ให้ template ฝั่ง server เติมชื่อ) (2) ทำ commercial agreement กับ Anthropic ที่มี DPA + zero data retention (3) เปิดเผยใน Privacy Notice และ DPA กับร้านว่ามี AI provider ใน US |

หมายเหตุ: การแจ้ง (notice) อย่างเดียว**ไม่พอ**สำหรับ ม.28 — ต้องมีมาตรการตามกฎหมายจริง (สัญญา/consent เฉพาะกรณีตาม ม.28(3)) ทางที่เสถียรที่สุดคือสัญญากับ sub-processor ทุกราย + เปิดเผยครบใน notice

| ขอเข้าถึง/รับสำเนา | 30 | **ขาด** — มี `GET /members/:id` แต่ไม่มี auth จึงไม่ใช่ช่องทางใช้สิทธิที่ปลอดภัย ต้องมี flow ยืนยันตัวตน + export ข้อมูลครบ |

| ระงับการใช้ | 34 | **ขาด** |
| แก้ไขให้ถูกต้อง | 35–36 | **ขาด** — ไม่มี endpoint แก้ไขข้อมูลสมาชิก (มีแต่ create) |
| ถอนความยินยอม | 19 วรรคห้า | **มีบางส่วน** — ลบ face ถือเป็นถอน consent ชีวภาพ แต่ไม่มีบันทึกการถอน และต้องถอนง่ายเท่าตอนให้ |

## 7. บทลงโทษและความเสี่ยงเมื่อขายให้เชนใหญ่

**โทษตามกฎหมาย:**
- **ปกครอง:** ม.82 (สูงสุด 1 ล้านบาท เช่น ไม่แจ้ง notice), ม.83 (สูงสุด 3 ล้านบาท เช่น ประมวลผลโดยไม่มีฐาน/ไม่มี DPA/ไม่แจ้งเหตุละเมิด), **ม.84 (สูงสุด 5 ล้านบาท — ฝ่าฝืน ม.26 ข้อมูลอ่อนไหว หรือส่งข้อมูลอ่อนไหวข้ามแดนโดยไม่ชอบ)** — กรณี Smart Cam Sale เกือบทุกความเสี่ยงหลักอยู่ในกลุ่ม ม.84
- **อาญา:** ม.79 — ใช้/เปิดเผยข้อมูลอ่อนไหวโดยไม่ชอบในลักษณะที่ทำให้เกิดความเสียหาย: จำคุกไม่เกิน 6 เดือน/ปรับไม่เกิน 500,000 บาท; เพื่อแสวงหาประโยชน์โดยมิชอบ: ไม่เกิน 1 ปี/1 ล้านบาท และ **ม.81 — กรรมการ/ผู้จัดการรับผิดส่วนตัว**หากเหตุเกิดจากการสั่งการหรือละเว้น
- **แพ่ง:** ม.77–78 — ค่าสินไหมทดแทน + ศาลสั่ง punitive damages ได้สูงสุด 2 เท่าของค่าเสียหายจริง

**ความเสี่ยงเฉพาะเมื่อขายเชน (CJ/7-11):**
1. **Scale คูณความเสี่ยง** — ระบบเดียวรันหลายพันสาขา = คนถูกสแกนหลักล้านต่อวัน เหตุละเมิดครั้งเดียวกลายเป็นข่าวระดับประเทศและเป็น test case ที่ สคส. เลือกดำเนินการ
2. **Vendor due diligence** — procurement ของเชนใหญ่จะขอ DPA, DPIA, ISO/มาตรการความปลอดภัย, ROPA, breach plan, รายชื่อ sub-processor — ปัจจุบันไม่มีสักอย่าง = ตกรอบ procurement ก่อนคุยราคา
3. **สัญญาผลักภาระ** — เชนใหญ่จะใส่ indemnity ให้ vendor รับผิดเต็มหากระบบทำให้เชนโดนโทษ — สถานะโค้ดปัจจุบัน (API เปิด, plaintext password) คือการรับ liability แบบไม่มีเพดาน
4. **False positive** — threshold match 0.55 (recognition.service.ts) ค่อนข้างต่ำ: การทักผิดคน/แสดงประวัติซื้อของคนอื่นบนหน้าจอพนักงาน = เปิดเผยข้อมูลส่วนบุคคลโดยมิชอบต่อหน้าลูกค้า

## 8. สรุป: สิ่งที่ต้องแก้ก่อนขาย

### ตาราง P0 — ต้องแก้ก่อนขาย (must-fix)

| # | รายการ | เหตุผล/มาตรา |
|---|---|---|
| P0-1 | เพิ่ม authentication + authorization ทั้ง REST API และ WebSocket; ปิด `broadcastFrame` แบบเปิด; จำกัด CORS | ม.37(1) — ปัจจุบันข้อมูลสมาชิกและภาพกล้องเข้าถึงได้สาธารณะ |
| P0-2 | ระบบบันทึกหลักฐาน consent: เวลา, เวอร์ชันข้อความ, ผู้ให้, ช่องทาง (แทน boolean `faceOptIn` เดี่ยว ๆ) + แบบฟอร์ม explicit consent สำหรับ face | ม.26, ม.19 — ภาระพิสูจน์อยู่ที่ฝั่งเรา |
| P0-3 | จัดทำ **DPA template** บริษัท↔ร้านค้า (รวมรายชื่อ sub-processor, หน้าที่แจ้งเหตุ, ขอบเขตห้ามใช้ข้อมูลเพื่อวัตถุประสงค์ตัวเอง) | ม.40 วรรคสาม — ไม่มี = ผิดทั้งสองฝ่ายตั้งแต่วันแรก |
| P0-4 | ทำ guest pipeline ให้ ephemeral จริง: ลบ embedding cache ของ guest ทันที (แก้ `lastEmbeddingByChannel/ByClient` ให้มี eviction และไม่เก็บของผู้ไม่ opt-in) + เอกสาร balancing test สำหรับ ม.24(5) | ม.26 — cache ปัจจุบันเก็บชีวภาพของผู้ไม่ยินยอม |
| P0-5 | Privacy Notice (สมาชิก + guest) และ **template ป้ายแจ้งหน้าร้าน** | ม.23 |
| P0-6 | จัดการข้ามพรมแดน: เก็บหลักฐาน SCC/DPA ของ Azure และ Neon; ทำ agreement กับ Anthropic (DPA/zero-retention) + **minimize payload ที่ส่ง Claude** (ตัด displayName/แต้ม ให้ server เติมชื่อใน template เอง) | ม.28–29, ม.84 |
| P0-7 | Breach response plan: ตรวจจับ → แจ้งร้าน (controller) ทันที → ร้านแจ้ง สคส. ใน 72 ชม. | ม.37(4), ม.40(2) |

### ตาราง P1 — ควรทำ (ก่อน scale / ขายเชน)

| # | รายการ | เหตุผล |
|---|---|---|
| P1-1 | Endpoint สิทธิเจ้าของข้อมูลครบชุด: ลบสมาชิกทั้งราย (cascade มีแล้วใน schema), แก้ไขข้อมูล, export/สำเนา, ระงับ/คัดค้าน | ม.30–36 |
| P1-2 | DPIA สำหรับ face recognition + ทบทวน threshold 0.55 / เพิ่มขั้นยืนยันก่อนแสดงโปรไฟล์ | ลด false positive = ลดการเปิดเผยผิดคน |
| P1-3 | แต่งตั้ง DPO และประกาศช่องทางติดต่อ | ม.41 — เข้าเกณฑ์ monitoring + ข้อมูลอ่อนไหว |
| P1-4 | ROPA ฝั่ง processor + template ให้ร้านค้า | ม.39, ม.40(3) |
| P1-5 | Retention policy: อายุ VisitLog (โดยเฉพาะที่ผูก memberId), ลบอัตโนมัติ | หลัก data minimization ม.37(3) |
| P1-6 | เข้ารหัสรหัสผ่านกล้อง (เลิก plaintext), audit log การเข้าถึงข้อมูลสมาชิก | ม.37(1) + ตอบ due diligence เชนใหญ่ |
| P1-7 | ข้อสัญญา limitation of liability / cyber insurance ก่อนเซ็นกับเชนใหญ่ | บริหารความเสี่ยง ม.77–78, ม.84 |

### เอกสารที่ต้องจัดทำ (checklist)

1. **แบบฟอร์มขอความยินยอมโดยชัดแจ้ง** (face embedding) — ภาษาเข้าใจง่าย แยกจากใบสมัครสมาชิก ถอนได้ง่าย
2. **DPA template** (บริษัท = processor ↔ ร้านค้า = controller) + ภาคผนวกรายชื่อ sub-processor (Azure, Neon, Anthropic)
3. **Privacy Notice** ฉบับสมาชิก และฉบับย่อสำหรับผู้เข้าร้าน (guest)
4. **ป้ายแจ้งหน้าร้าน** (template ให้ทุกร้านติดก่อนแนวกล้อง)
5. **ROPA** (ฝั่ง processor + template ฝั่ง controller)
6. **DPIA report** สำหรับระบบ face recognition
7. **Incident/Breach response plan** (รวม SLA แจ้งร้านและ flow 72 ชม.)
8. เอกสาร **balancing test** สำหรับ guest analytics (ฐาน ม.24(5))
